### R-016

The supervisor loop has three phases. Phase 1 (locked) takes a `Snapshot`, phase 2 (unlocked) does the probe, SLP, RCON TPS and sysinfo work, and phase 3 (locked) writes back the result. Phase 2 can take anywhere from milliseconds to about 2.5s when the timeouts fire.

1. Phase 1: `snapshot.state = Online`.
2. During phase 2 the user clicks Stop. `stop_server` takes the lock, `mark_stopping` sets `runtime.state = Stopping` and `stop_requested = true`, writes `stop` to stdin, and releases the lock.
3. Phase 3: `new_state = next_state(Online, has_child=true, accepting=true) = Online`. `sleep_now` is false (or blocked by `!stop_requested`), so the `else if runtime.state (Stopping) != new_state (Online)` branch runs: `runtime.state = Online`, and an `online` event is emitted.

The UI shows `online` again until the process exits, which can take up to the 10s grace period. Escalation still works because it keys off `stop_requested`. During `Starting` the same thing reverts `Stopping` to `starting`. `sleep_server`, `restart_server`, `force_kill_server`, `force_kill_all_servers` and a console `stop` all go through `mark_stopping`, so they're affected the same way.

### R-018

All of these write to the map under `key` without checking that the runtime is still the one they were acting for:

- `sleep_listener.rs:239-241` (wake failed): `guard.remove(&params.key)`.
- `supervisor.rs:473-476`: after `spawn_sleep_listener`, sets `runtime.sleep_stop` on whatever entry is under `key`.
- `supervisor.rs:487-489` (listener bind failed): `guard.remove(&key)`.
- `runtime.rs:758-760` (force-kill of an adopted server): removes the key after the unlocked `netstat` + `taskkill`.

Example interleaving:

1. A server is `Sleeping`. A player joins, so the listener calls `wake_server`, which waits for the port to free.
2. Meanwhile the user clicks Start. `start_server_internal` (on the main thread) removes the sleeping entry, spawns java, and inserts runtime G2.
3. The wake's `start_server_internal` finds G2's child alive and returns `Err("Server is already running.")`.
4. `wake_server` then runs `guard.remove(&params.key)` (removing G2) and emits `offline`.
5. G2's supervisor sees `None` and exits. The java process keeps running with no runtime record, so Stop can't reach it, and the UI shows `offline` until a later `get_server_runtime` adopts it as `running-external`.

This overlaps with R-024. Fixing that race (reserving the key) narrows this one but doesn't remove it.

### R-024

1. Thread A (for example the restart thread at runtime.rs:696, polling every 200ms) and thread B (a second restart thread from a double-click, or the auto-restart / wake / `start_server` command) both see no live child.
2. A locks at :339, finds no entry (or removes the stale one), and unlocks. B does the same.
3. Both resolve args, Java and RCON, and both `spawn()` a JVM.
4. A inserts G1 at :465 and starts supervisor G1. B inserts G2 at :465, overwriting G1. A's `Child` is dropped without being killed.
5. Supervisor G1 sees a generation mismatch and exits. JVM #1 keeps running untracked (the job object kills it only when mserve exits), and JVM #2 fails on the port bind or `session.lock` and shows as `crashed`.

On the wake path the entry is removed at :353 and only reinserted after the ~6s port-free wait at :359-366, so the window there is seconds wide, not milliseconds.
